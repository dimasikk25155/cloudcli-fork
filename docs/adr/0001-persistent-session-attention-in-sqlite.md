# 0001. Персистентный статус сессий в SQLite с одной точкой подключения в реестре прогонов

**Статус:** принято, 2026-10-12

## Контекст

Нужно понимать, какая сессия работает, ждёт ответа, закончила или упала (R01–R10).
Статус должен переживать перезагрузку страницы и рестарт сервера и быть виден с любого
устройства. Сейчас «жёлтая точка» живёт в памяти клиента, а реестр прогонов держит
прогоны в памяти около 5 минут. Движков три (Claude, Codex, Grok), у каждого свой путь
событий. Соединения WebSocket не знают, какой пользователь за ними стоит.

## Решение

- Новый серверный модуль `session-attention` с таблицами статуса и «просмотрено» в
  существующей SQLite через обычный механизм схемы и миграций.
- Единственная точка подключения — запись события в реестре прогонов (через неё идут все
  движки) плюс старт прогона. Вопросы и планы Grok видны там же как запрос разрешения.
- Реестр начинает хранить пользователя, запустившего прогон; строка статуса знает автора.
- Концовка хода классифицируется чистой функцией на регулярках RU/EN по последнему
  тексту ассистента (вопрос / просьба сделать руками / ничего), без модели.
- При старте сервера статус сверяется с реальностью: «работает» без живого прогона и
  «ждёт» у Claude становятся «упало: прервано»; «ждёт» у Grok — «ждёт: вопрос текстом» с
  сохранённым вопросом (уточнено на таске 01: ожидающие запросы теряются при рестарте).
- Клиент получает широковещательный сигнал «изменилось» с одним идентификатором сессии
  без содержимого и перечитывает список через API с фильтром доступа; страховка — опрос
  раз в 20 секунд.

## Рассмотренные варианты

- **Расширить память реестра прогонов** — не переживает рестарт, отвергнуто.
- **Подключать каждый движок отдельно** — три точки правки и расхождение логики;
  реестр уже является общим горлышком.
- **Отдельное хранилище (файл, Redis)** — новая зависимость без выигрыша, SQLite уже есть.
- **Классифицировать концовку локальной моделью** — статус нужен мгновенно и без
  зависимости от Windows.
- **Слать содержимое статуса по WebSocket** — соединение не знает пользователя, утечка
  чужих вопросов.

## Последствия

- Фоновые прогоны (расписания, пайплайны, Telegram-промпты) идут мимо реестра и в хаб не
  попадают — сознательно вне рамок.
- Реестр прогонов становится критичной точкой: любая его переделка обязана сохранить
  вызовы статуса и передачу пользователя.
- Классификатор на регулярках ошибается на нестандартных формулировках; покрыт тестами
  на реальных фразах, расширяется правкой правил.
- Отмена потребует миграции схемы назад и возврата клиентской точки на память.
