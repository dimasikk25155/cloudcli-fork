# 0029. Доставка пачки мастер-сессии хранится в workspace_records

**Статус:** принято

## Контекст

Защита от двойной отправки пачки держалась в памяти процесса: `Map` с ключом `userId:batchId:sessionId`, TTL 24 ч, максимум 2000 записей. После рестарта сервера повторное нажатие отправляло пачку второй раз. Хранилище `workspace_records` уже есть и индексировано по `(owner_user_id, kind)`.

## Решение

Результаты доставки пишутся в `workspace_records` с kind `master-send` (владелец — пользователь, ключ тот же, TTL 24 ч) через зависимость `MasterSendLedger` (`get/put/prune`). Память остаётся только для отправок «в полёте». Провал, кроме forbidden, не запоминается, чтобы повтор был возможен. Клиент генерирует `batchId` на одно нажатие «Отправить».

## Почему

Отвергнуто: новая таблица — ради одного короткоживущего ключа это миграция и новая схема, а существующий универсальный стор подходит. Отвергнуто: оставить `Map` и дольше хранить — не переживает рестарт, ради которого задача. Отвергнуто: файл на диске — вторая система хранения, без транзакций.

## Последствия

Таблица `workspace_records` получает записи не по её исходному назначению, а чистка выполняется самим `prune` по TTL, без внешнего планировщика. Запись и отправка в чат не атомарны: падение между ними оставит либо дубль, либо потерянную доставку, и защита этого не закрывает. Тест с «рестартом» проверяет новый сервис на том же сторе, а не реальный перезапуск процесса.
