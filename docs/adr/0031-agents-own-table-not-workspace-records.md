# 0031. Агенты хранятся в своей таблице, а не в workspace_records

**Статус:** принято

## Контекст

Универсальное хранилище `workspace_records` не требует миграции и годится для `kind:'bot'`. У агента есть связи: чат и тред принадлежат агенту, правила памяти имеют номера версий.

## Решение

Агенты, правила памяти и привязка «агент ↔ сессия» живут в трёх своих таблицах. Версия агента считается по правилам: «Vn» — набор правил, живых на версии n, правила не удаляются физически, а помечаются снятыми.

## Почему

Отвергнут `workspace_records`: payload в JSON не даёт внешних ключей, каскадного удаления агента вместе с правилами и быстрой выборки «чьи это сессии» для сайдбара. Версии правил пришлось бы склеивать вручную внутри JSON с оптимистичными ревизиями на каждую правку. Отвергнута привязка через поле в таблице сессий: сессии принадлежат другим модулям, лишняя колонка там тянет миграцию чужой таблицы. Связь без внешнего ключа на сессии сделана сознательно, чтобы удаление чата не трогало агента.

## Последствия

Это ещё одна схема со своей миграцией: откат выкатки не уберёт таблицы, они останутся пустыми. Уникальность имени без учёта регистра для кириллицы держит сервис, а не индекс, и параллельные записи способны её обойти. Список моделей агентов скопирован из тредов, чтобы не было цикла зависимостей, и расходится с ними при их правке. Удалённые правила остаются в базе навсегда ради истории версий.
