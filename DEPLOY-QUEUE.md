## В очереди

### 2026-07-27 — «API Error: 529 Overloaded» больше не убивает прогон
- **Что:** прогон умирал с красной плашкой «Прогон прерван — Причина: API Error:
  529 Overloaded», и всю работу приходилось запускать заново руками. Особенно
  больно на воркфлоу: 12 агентов отработали 50 минут, а финальный синтез упал —
  и весь результат в мусор. В логе таких падений 5 подряд.
- **Причина (не «просто перегрузка»):** сам Claude Code при 529 сдаётся раньше,
  чем мог бы. В его коде: (1) потолок ретраев 10; (2) если сервер просит ждать
  слишком долго — бросает `retry_after_too_long`; (3) в фоновых подзапросах
  (компактизация, сабагенты, воркфлоу) 529 **вообще не ретраится** — его
  собственная телеметрия называет это `api_request_overload_background_dropped`.
  Всё это включается обратно недокументированной ручкой самого CLI —
  `CLAUDE_CODE_RETRY_WATCHDOG`: с ней потолок 300 ретраев, mid-stream 529
  переретраивается, длинные паузы отрабатываются как надо.
- **Фикс, слой 1 (корень):** `server/claude-sdk.js` → `mapCliOptionsToSDK` шлёт
  CLI `CLAUDE_CODE_RETRY_WATCHDOG=1` (можно перебить своей env-переменной).
- **Фикс, слой 2 (страховка):** если прогон всё же умер от временной ошибки
  (529 / 5xx / оборванное соединение), цикл прогона сам повторяет ход на ТОЙ ЖЕ
  сессии с растущей паузой — 5с, 20с, 60с, 120с (`TRANSIENT_RETRY_DELAYS_MS`),
  показывая в чате мягкое «⏳ повторяю сам, делать ничего не надо» вместо
  красной ошибки. Лимит подписки, отсутствие CLI, проблемы с оплатой/ключом
  под ретрай НЕ попадают (`isTransientRunFailure` в `shared/run-outcomes.ts`) —
  их повтор не лечит, поэтому они по-прежнему сразу видны пользователю.
  «Стоп» во время паузы работает: на время ожидания в реестр сессий кладётся
  заглушка с `interrupt()`, иначе кнопка молчала бы всю паузу.
- **Если все повторы не помогли** — плашка остаётся, но с человеческой
  причиной: «серверы Anthropic перегружены (529) — автоповторы не помогли».
- **Тесты:** +5 в `server/shared/tests/run-outcomes.test.ts` (что ретраим, что
  нет, тексты). Весь набор — 203/203 зелёные, typecheck чистый.

### 2026-07-24 (2) — фикс залипания режима разрешений между разными чатами
- **Что:** включаешь «Режим планирования» (или любой другой) в одном чате — он
  продолжает действовать и в других чатах, которые никогда сами такой режим не
  выбирали. По просьбе Димы: режим должен храниться СТРОГО по одному чату,
  вообще без общих/промежуточных ключей.
- **Причина:** `selectPermissionMode` при каждом выборе писал глобальный ключ
  `permissionMode-last-${provider}` (последний выбранный где угодно), а при
  открытии чата без СВОЕГО сохранённого режима код падал именно на этот
  глобальный ключ вместо дефолта провайдера — отсюда «утечка» между
  несвязанными чатами. Первая версия фикса (промежуточный «pending» ключ)
  всё ещё могла утечь в редком случае: начал новый чат → выбрал режим → НЕ
  отправил → переключился на другой старый чат — тот мог подхватить чужой
  ещё не пристроенный выбор.
- **Фикс (финальная версия):** единственный ключ — `permissionMode-${sessionId}`,
  свой на каждый чат, без исключений. У нового неотправленного чата (id ещё
  нет) выбор живёт только в состоянии React; в момент, когда чат получает
  свой первый реальный id (`onSessionEstablished` в `ChatInterface.tsx`),
  текущий режим записывается СРАЗУ под этот id (`commitPermissionModeToSession`) —
  и только под него. Никакого общего/подвешенного ключа больше нет вообще.
  Отдельный ref-предохранитель (`draftPermissionModePickedRef`) не даёт фоновой
  подгрузке `/api/providers/capabilities` затереть уже сделанный в черновике
  выбор до отправки (актуально на медленном мобильном соединении).
- **Файлы:** `src/components/chat/hooks/useChatProviderState.ts`,
  `src/components/chat/view/ChatInterface.tsx`
- **Проверено:** `tsc --noEmit` чисто. Ключи `permissionMode-*` больше нигде в
  коде не используются (проверено grep) — менять схему безопасно.

### 2026-07-24 — фикс мёртвых тапов в списках Модель/Уровень/Режим на мобиле (APK)
- **Что:** на телефоне (проверено на установленном APK) список не закрывался и выбор
  не применялся при тапе на пункт — сам список висел открытым, будто тап не долетал.
- **Причина:** пункты списка лежат в `overflow-y-auto`-контейнере; на реальном тач-
  устройстве браузер трактует даже небольшое дрожание пальца во время тапа как начало
  скролла этого контейнера и глушит синтетический `click` целиком — обработчик выбора
  просто не срабатывает. `touchend` при этом всегда стреляет вне зависимости от этой
  эвристики.
- **Фикс:** добавлен `tapSelect()` — на тач-устройствах выбор делает `touchend`,
  на мыши/клавиатуре — как раньше `onClick`; suppress-ref (та же схема, что уже
  есть в `useMobileMenuHandlers.ts`) не даёt сработать выбору дважды, если браузер
  всё же довёл `click` до конца. Применено ко всем трём спискам (режим разрешений,
  модель, уровень размышлений) — все три используют один и тот же паттерн.
- **Файл:** `src/components/chat/view/subcomponents/ChatComposer.tsx`
- **Проверено:** `tsc --noEmit` чисто; сама механика (pointerdown-детектор чужого
  клика не мешает тапу по пункту меню) прогнана headless Chromium с touch-эмуляцией
  на изолированной копии разметки — тап по пункту корректно закрывает список и
  меняет выбор.

### 2026-07-21 (вечер) — фикс гонки авто-обновления CLI ("exists but failed to launch")
- **Что:** Claude Code CLI сам себя обновляет (подменяет файл + symlink `~/.local/bin/claude`);
  если CloudCLI спавнит процесс в этот момент — `existsSync()` проходит, но запуск падает,
  SDK кидает "Claude Code native binary at <path> exists but failed to launch".
  `autoUpdates:false` не спасает (есть `autoUpdatesProtectedForNative:true`).
- **Фикс:** retry на один повтор (800мс задержка) именно на этой ошибке, и только пока
  в стрим ещё ничего не пришло (безопасно повторить без дублей).
- **Файл:** `server/claude-sdk.js`
- **Проверено:** typecheck чисто, 165/165 тестов зелёных. Подробности — вольт Dimasik,
  заметка `wiki/entities/agents-web-ui.md`.
